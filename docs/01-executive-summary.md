# Executive Summary — Approach & Trade-offs

**Deliverable C · ~340 words**

My strategy is risk-based: every scenario is weighted by its distance from revenue. The single most valuable journey on Amazon is Search → PDP → Add to Cart → Checkout entry, so I tested that path deepest — positive, negative, and under degraded conditions (Slow 3G, offline mid-flow, back/forward/refresh, multi-tab) — rather than spreading effort thinly across the site.

**Prioritised:** (1) Cart/Checkout state integrity — highest risk because failures cost money directly and state bugs (stale badge, lost cart on refresh, duplicate submission) are the most common regression class after a flow redesign; (2) Search relevance, filter/sort combinations and URL-reflected state — the top-of-funnel entry point; (3) PDP variant switching correctness — wrong price/image per variant erodes trust and drives returns; (4) Accessibility of the buy path (keyboard-only, ARIA) — legal exposure plus a real conversion segment.

**Deliberately skipped:** full payment submission (rules forbid real payment data; risk of placing real orders), account settings/Prime/Fresh (out of assignment scope), ranking-quality evaluation (non-deterministic, A/B-served, needs analytics not black-box QA), full cross-browser matrix (Chrome desktop + mobile viewport deep, Firefox smoke only — engine share justifies the cut in a 6-hour box).

**Real-world Amazon considerations that shaped the work.** I verified the live DOM before writing a line of automation: Amazon exposes almost no `data-testid` (0 on the homepage), but provides stable semantic IDs (`#twotabsearchtextbox`, `#add-to-cart-button`, `#sc-buy-box-ptc-button`), `data-component-type="s-search-result"`, `data-asin`, and `data-cy` hooks on search cards — my locator hierarchy is built on these plus ARIA roles, never on generated class chains. Automation must survive anti-bot interstitials (CAPTCHA "dog page"), the delivery-location popover, and A/B DOM variants — handled with realistic locale headers, popup-dismissal helpers, and web-first assertions instead of sleeps. Prices/tax are location-dependent, so assertions parse values rather than hardcode them. Guest checkout is asserted up to the auth redirect — never past it.

**What the strategy found.** Five defects, all reproduced live: a cart line that dead-ends in a permanent spinner with no error and no retry when the quantity-update request fails, while checkout stays enabled (High/P1); a price-range filter set to $20–$84 that returns items displayed at $8.69–$15.85, because the refinement matches the featured price while the card renders the used & new offer price (High/P2); a "Price: Low to High" sort that ranks price-less, un-actionable cards above the priced ones (Medium/P2); two contradictory delivery destinations rendered in the same frame (Medium/P2); and a "Compare with similar items" widget that offers makeup sponges as comparables for a wireless mouse (Medium/P2). Two of the five share one root cause — refinements evaluated against a price the card never shows — so they are recommended as a single fix. Equally important, two of my initial hypotheses — sort resetting after filtering, and server-side cart corruption on network failure — were tested and **did not reproduce**; both are documented as ruled out. Knowing what is *not* broken is part of the deliverable.

**With more time:** WebKit/Firefox full matrix, NVDA/VoiceOver screen-reader pass, API-level checks on the suggestions endpoint, visual regression on PDP breakpoints, and soak-testing cart concurrency across sessions.
